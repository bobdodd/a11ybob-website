1. Meter (role="meter")

These tests validate accessible names for elements with role="meter". Meters are used to represent scalar measurements with a known range.

⚠️ Understanding the Meter Role

According to the WAI-ARIA specification, the role="meter" represents a scalar measurement within a known range, similar to an HTML <meter> element. Key implementation requirements include:

  • The meter must have an accessible name via aria-label or aria-labelledby
  • It should use aria-valuemin, aria-valuemax, and aria-valuenow to communicate its values
  • Optionally, aria-valuetext can provide a human-readable text alternative of the value
  • Visual presentation should indicate the meter's value within its range
  • The meter widget itself should not be focusable or interactive (it's a read-only indicator)

Important: While HTML provides a native <meter> element that should be used when possible, the ARIA meter role is needed when creating custom meter widgets or retrofitting existing elements.

2. Toolbar (role="toolbar")

These tests validate accessible names for elements with role="toolbar". Toolbars are containers for groups of buttons or other interactive controls.

⚠️ Understanding the Toolbar Role

According to the WAI-ARIA Authoring Practices Guide (APG), the role="toolbar" is a container for grouping a set of commonly used controls. Key implementation requirements include:

  • The toolbar should have an accessible name via aria-label or aria-labelledby
  • It should contain buttons, toggle buttons, or other interactive controls
  • It may use aria-orientation to indicate its orientation (horizontal by default)
  • Keyboard support must allow navigation between items using arrow keys
  • Related items can be grouped using role="group" with proper labeling

Important: A toolbar is different from a menubar in that it is always visible and contains buttons, while a menubar contains dropdown menus. Toolbars are commonly used in document editing software, drawing applications, and other interfaces with many user actions.

3. Tree (treeview pattern)

These tests validate accessible names for elements with role="tree" and role="treeitem". Trees are hierarchical lists that allow users to navigate through and select nested content.

⚠️ Understanding the Tree Role

According to the WAI-ARIA Authoring Practices Guide (APG), a role="tree" represents a hierarchical list with nested groups that can be collapsed and expanded. Key implementation requirements include:

  • The tree container must have an accessible name via aria-label or aria-labelledby
  • It contains elements with role="treeitem"
  • Parent treeitems should use aria-expanded to indicate their state
  • Each treeitem may use aria-level, aria-setsize, and aria-posinset to define its position in the hierarchy
  • Only one treeitem should be in the tab sequence at a time
  • Keyboard navigation must allow for both vertical traversal and expanding/collapsing nodes

Important: Trees are often used for navigation menus, file systems, site maps, or other hierarchical data structures where users need to navigate through multiple levels of information.

4. Accessible Names with Tabindex (Non-Standard Patterns)

These tests validate accessible names for elements that use tabindex to make them focusable, even when the ARIA role is incorrect or non-interactive. This tests whether screen readers can announce something meaningful when focusing these elements.

⚠️ Understanding Tabindex and Accessible Names

When elements have tabindex="0" or tabindex="-1", they become programmatically focusable, which means screen readers may announce them. Having an accessible name for these elements is important even if the role is incorrect or non-standard:

  • tabindex="0" adds the element to the tab sequence, allowing users to focus it with keyboard navigation
  • tabindex="-1" makes the element programmatically focusable but not in the tab sequence (usually for focus management)
  • Elements with incorrect or non-interactive roles still need accessible names when they're focusable
  • The lack of an accessible name on a focusable element can result in confusing or meaningless announcements

Important: While these tests validate accessible name computation, they do NOT represent best practices for ARIA usage. In production code, always use the correct ARIA roles that match the element's purpose and behavior.
