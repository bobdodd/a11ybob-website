The thirty-eight terms [clause 5](/adaptation/afds/specification/part-1#c5) defines, which carry these meanings and no other wherever a normative clause uses them.

[Clause 5](/adaptation/afds/specification/part-1#c5) is normative, and it says how to read itself: where a term defined there is used in a normative clause, "it carries this meaning and no other".
[Clause 5](/adaptation/afds/specification/part-1#c5) defines thirty-eight terms.
All thirty-eight are below, in the specification's own words or a close paraphrase.

**Accessibility Focused Design System (AFDS).**
"A design system whose accessibility contract, supporting evidence, and recorded uncertainty are first-class parts of the system rather than documentation about it."

That sentence is the whole project in one line.
The distinguishing move is not that the components are accessible.
It is that the contract, the evidence and the uncertainty are parts of the system — versioned, addressable, shipped — rather than prose written about the system afterwards and left behind when the system travels.

**AFDS package.**
A single file conforming to [Part IV](/adaptation/afds/specification/part-4), containing a declared hierarchy of artefacts and the two required root artefacts.

Four of these terms are worth pausing on now, because later sections rely on them and a reader who skims the table will not have absorbed them.

*Uncertainty record* is defined as being "of the same standing as a record stating a result".
That standing is deliberate, and [clause 17](/adaptation/afds/specification/part-2#c17) depends on it.

*Non-guarantee* exists because of an asymmetry in how people read documentation: a component that lists only what it promises invites a reader to assume the rest.
[Clause 14](/adaptation/afds/specification/part-2#c14) makes the refusals explicit for that reason.

*Native baseline* is a disclosure, not a design preference: it names what the component would have done if built from platform-native elements without added roles or scripted behaviour, so that the cost of not doing so can be seen (clauses [5](/adaptation/afds/specification/part-1#c5), [8.3](/adaptation/afds/specification/part-2#c8-3)).

*Composition conformance* is a different measurement from component conformance, not a stronger one.
It is conformance measured with the component inside a realistic page.

<h2 id="a-note-on-component-specification">A note on "component specification"</h2>

This phrase used to mean two different things in the specification, and if you have read an earlier edition of either document you will have met the collision.

[Clause 5](/adaptation/afds/specification/part-1#c5) defined a component specification as the *human-readable* counterpart to a component contract, while [clause 7.1](/adaptation/afds/specification/part-2#c7-1) defined it as the *machine-readable* JSON record — and [clause 7.5](/adaptation/afds/specification/part-2#c7-5) compounded it by requiring that "every component specification *SHOULD* have a human-readable counterpart", which under [clause 5](/adaptation/afds/specification/part-1#c5)'s definition asked every prose document to have a prose document.

That is settled, and the three terms now name three different things ([clause 5](/adaptation/afds/specification/part-1#c5)).

The resolution followed usage rather than the glossary: the manifest already pairs a `specification` path with a `documentation` path, the filename convention is `.spec.json`, and [clause 28.1](/adaptation/afds/specification/part-4#c28-1) already had a `documentation` artefact role.
The project's reasoning, and what it cost, are recorded in `docs/COLOPHON.md`.

One consequence is worth carrying with you.
Because the contract is the commitments rather than the file, a clause that speaks of placing or reading a component contract is speaking of the specification that carries it, and both readings are true.
